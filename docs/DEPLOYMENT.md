# Deployment — Vercel + a GitHub org

How to run the Digital Unit Portal for real: the GitHub **organization** it lives
in, the repositories it reads and writes, the **GitHub App** identity, and the
**Vercel** project. The design principle throughout: **credentials are server-side
only** (constraint #7), and **no automation merges a pull request** (constraint #1)
— the human merge under `CODEOWNERS` is the governance boundary.

Until the App and keys are provisioned, the portal runs fully **offline**: a local
git workspace stands in for GitHub and a deterministic engine stands in for the
model. So you can deploy first and turn the live paths on later, one env var at a
time — no code change.

---

## 1. The GitHub organization

Create (or use) one org, e.g. `digital-unit`. It holds four kinds of repository:

| Repository | Purpose | Who writes | Merge policy |
|---|---|---|---|
| `digital-unit.portal` | The portal app (this repo). Deployed to Vercel. | humans (PRs) | PR + review on `main` |
| `du-demands` | **Intake funnel** — every demand/case is a folder (`README.md`, `requirements.md`, `analysis.md`, `research.md`). | the portal App, to `main` | App writes `main` directly (not a gated repo) |
| `du-agent-registry` | Skills & Playbooks registry, edited in-app. | the portal App, to `main` | second-approver via `CODEOWNERS` |
| `uc-YYYY-NNNN-<slug>` | A use case's own repo — created only at the **PoC stage**. | the portal App (branches + PRs) | **human** merge under `CODEOWNERS` — the gate |

Naming is configurable by env (`DEMANDS_REPO`, `REGISTRY_REPO`); the `uc-*` names
are generated by `lib/poc/scaffold.ts`.

### Teams (map to `CODEOWNERS`)

`lib/codeowners.ts` generates ownership for `uc-*` repos with **no gatekeeper role**
(a deliberate deviation — G3–G5 authority sits with the portfolio forum). Create:

- `@digital-unit/du-triage` — G1/G2
- `@digital-unit/portfolio-forum` — G3–G7 (unscoped)
- `@digital-unit/it-liaison` — run-lane handovers
- `@digital-unit/du-value` — value tracking

### Branch protection (this is the governance, not decoration)

- **`uc-*` `main`**: require a pull request, require review from `CODEOWNERS`,
  dismiss stale approvals, **no** auto-merge, **no** bypass for apps. This is what
  makes a gate a human act. The portal App can open PRs here but must **not** have
  merge rights.
- **`digital-unit.portal` `main`**: require a PR + review; CI (below) required.
- **`du-demands` / `du-agent-registry` `main`**: the App writes here directly (the
  funnel and registry are not gated use-case repos). Restrict who else can push;
  the registry's sensitive paths (`skills/`, `playbooks/`) get a `CODEOWNERS`
  second approver if you route its edits through PRs instead of direct save.

## 2. The GitHub App (one fleet-wide identity)

Full walkthrough in [`SETUP-github-app.md`](./SETUP-github-app.md). In short:

- **Permissions**: Administration (create repos) R/W, Contents R/W, Pull requests
  R/W, Metadata R. **Never** grant a merge workflow.
- **Install** on the org, scoped to `du-demands`, `du-agent-registry`, and `uc-*`.
- **Webhook** → `<portal>/api/webhooks/git` with `GITHUB_WEBHOOK_SECRET` (for the
  reconciler; optional until you enable webhook-driven reconciliation).
- Download the `.pem` private key.

The portal switches from the local workspace to the live App automatically once
`GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_APP_INSTALLATION_ID`, and
`GITHUB_ORG` are all present (`hasGitHubCredentials`).

## 3. Vercel project

1. **Import** `digital-unit.portal` into Vercel (New Project → import the repo).
   Framework auto-detects **Next.js**; `vercel.json` pins the region to **`fra1`**
   (Frankfurt, EU) — change it to another EU region if you prefer, but keep it in
   the EU (the model and data-processing terms assume EU routing).
2. **Build**: default (`next build`); Node from `.nvmrc` (20).
3. **Environment variables** (Project → Settings → Environment Variables) — set from
   `.env.example`. All are **server-side**; none are `NEXT_PUBLIC_*`, so nothing
   reaches the browser bundle:
   - Model: `ANTHROPIC_API_KEY` (+ optional `ANTHROPIC_BASE_URL`, `ANTHROPIC_MODEL`)
     and/or `OPENAI_API_KEY`; optional `MODEL_PROVIDER` override.
   - GitHub App: `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` (paste the full multi-line
     `.pem`; Vercel preserves newlines — the code also accepts `\n`-escaped),
     `GITHUB_APP_INSTALLATION_ID`, `GITHUB_ORG`, `GITHUB_WEBHOOK_SECRET`.
   - Repos: `DEMANDS_REPO=du-demands`, `REGISTRY_REPO=du-agent-registry`.
   - Auth (when wired): `AUTH_SECRET`, `OIDC_*`.
   - Ops: `KV_REST_API_URL`/`KV_REST_API_TOKEN` (playbook state), `CRON_SECRET`,
     `AGENT_TOOLS` (`off` is the global kill switch).
4. **Preview vs Production credentials.** Give **Production** the live keys. Give
   **Preview** either nothing (so previews run offline) or a **sandbox** App +
   sandbox org — never production write credentials. Preview deployments must not be
   able to write the real funnel or open real PRs (sandbox-first, `12 §12.11`).

### Regions & data residency

- App region: `fra1` via `vercel.json`.
- Model: set `ANTHROPIC_BASE_URL` to your EU endpoint if you use one.
- All GitHub/model calls run in server routes (`runtime = "nodejs"`), so keys stay
  on the server.

## 4. CI (portal repo)

`.github/workflows/ci.yml` runs on every PR and push to `main`:

- `typecheck` → `test` → `build` (the build must succeed with **no** credentials —
  proving the offline path stays intact).
- a **no-merge guard**: greps the codebase for any merge call and fails if one
  appears — constraint #1 enforced in CI, not just by convention.

Make the `build` and `guard-no-merge` jobs **required status checks** on
`digital-unit.portal`'s branch protection.

> Note: this CI is for the **portal app**. Use-case repos deliberately have **no**
> markdown-validation CI — that enforcement is portal-side (the recorded deviation
> from the spec's CI-based model).

---

## 5. Go-live order (each step is independent)

1. Deploy to Vercel **offline** — the whole UI works against seed data and local
   workspaces. Verify the pages render and the model-status chip reads "Offline".
2. Add a **model key** → the assistant, intake, and research agents reason live;
   the chip flips to the provider. No redeploy logic needed.
3. Create `du-demands` + `du-agent-registry`, install the **GitHub App**, set its
   four env vars → intake saves and registry edits hit real repos; the PoC builder
   creates real `uc-*` repos and opens real PRs.
4. Wire **OIDC** (`AUTH_SECRET`, `OIDC_*`) → real sessions replace `DEMO_SESSION`;
   `can()` resolves roles from group claims.
5. Enable the **webhook** + a reconciler cron (`CRON_SECRET`) → the registry cache
   stays in sync with the fleet.

## What never changes across environments

- Credentials never reach the browser (all server-side).
- No route, tool, or function merges a pull request — the `GitHost` interface has no
  merge method, and CI guards against one being added.
- Value figures carry their confidence state; the offline and live paths produce the
  same standardized markdown.
