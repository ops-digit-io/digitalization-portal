# 13 — Security

## 13.1 Trust domains

```
Domain A: user ↔ portal        corporate identity provider, OIDC
Domain B: portal ↔ repositories application identity
Domain C: portal ↔ model        service credential
```

Separate by design. A compromised user session cannot reach repository
credentials. The application identity is exercised only under an authorized
session or a named service identity. No user ever holds a repository credential
through the portal.

## 13.2 Authentication

- Corporate identity provider only. No local accounts, no password path, no
  invite links.
- Tenant identifier pinned in configuration; no other directory can authenticate.
- Session as a signed, httpOnly, SameSite=Strict cookie. Short lifetime, silent
  renewal.
- Group claims mapped to roles at session creation and re-resolved per request
  ([04](04-rbac.md)).
- No fallback authentication path. If the identity provider is unavailable, the
  portal is unavailable. This is deliberate: an emergency-access path is the
  route by which such systems are actually compromised.

## 13.3 Authorization

Middleware gates routes. **Middleware is not authorization.** Every handler
re-derives capability from the session for the specific action and context.

```
middleware        → is there a session at all?
route handler     → does this session hold this capability, for this plant,
                    for this gate, and is this not self-approval?
CI in repository  → independently re-enforces sequence, confidence, and
                    separation rules
```

Three independent layers. Compromising the application defeats the first two and
not the third, because CI runs in the repository platform under rules the portal
cannot alter.

## 13.4 The gate boundary

The most security-relevant property in the system:

**No API route merges a pull request. No tool merges a pull request. No merge
capability exists in the application identity's exercised surface.**

Consequences:

- An attacker with full portal compromise can open gate pull requests. They
  cannot pass gates.
- An attacker with a valid session at any privilege level cannot pass a gate
  without a code owner's merge.
- A prompt injection that convinces the agent to pass a gate fails, because no
  such tool exists to call.

Gate authority lives in the repository platform's code-owner enforcement, outside
the portal's blast radius.

## 13.5 Secrets

| Secret | Storage | Rotation |
|---|---|---|
| Application identity private key | Platform encrypted environment, production scope | Annual, or on suspicion |
| Webhook signing secret | Platform encrypted environment | Annual |
| Model service credential | Platform encrypted environment | Annual |
| Session signing key | Platform encrypted environment | Quarterly |
| Cron shared secret | Platform encrypted environment | Quarterly |
| Integration keys (mail/chat automation) | Per-integration, revocable individually | On personnel change |

Rules: never in the repository, never in client bundles, never in logs, never in
preview environments. Access tokens minted per request with short lifetime, never
persisted.

## 13.6 Webhook endpoint

The only publicly reachable unauthenticated route, and therefore the most
defensive.

```
1. Read raw body before any parsing
2. Verify HMAC signature against the stored secret
3. Constant-time comparison
4. Reject with 401 and no processing on mismatch
5. Check delivery identifier against a replay window
6. Only then parse
```

Signature verification happens before body parsing so that a malformed or
malicious payload is never deserialized on an unverified request.

## 13.7 Input handling

| Input | Treatment |
|---|---|
| Intake text | Stored as data. Never evaluated, never interpolated into a template with executable semantics. |
| Retrieved artifacts | Wrapped in `<external_content>` before reaching the model ([08.6](08-ai-architecture.md#86-untrusted-content)). |
| YAML from repositories | Safe-loaded. No custom tags, no object construction. |
| Slugs and identifiers | Generated by the portal from a restricted character set. Never taken from user input directly. |
| File paths | Never constructed from user input. Artifact paths come from the stage machine. |

## 13.8 Prompt injection

Treated as a first-class threat, because intake text is untrusted by definition —
any employee can submit it, and mail-channel intake can carry externally authored
content.

**Controls:**

1. All retrieved content wrapped by the retrieval layer, not by the model.
2. System prompt states wrapped content is data, never instruction
   ([09](09-system-prompt.md)).
3. Structural: the agent cannot pass a gate regardless of what it is convinced
   of, because no tool exists.
4. Authority is session-derived, never content-derived. Content claiming
   administrator authority changes nothing.
5. Every agent action produces a pull request that a human reviews.
6. Evaluation set includes injection cases; they must pass before any prompt or
   skill change merges.

**Residual risk.** A sophisticated injection could cause the agent to draft a
misleading business case that a reviewer merges without close reading. The
mitigation is procedural, not technical: agent-produced pull requests are
labelled `agent-proposed`, and the agent is instructed to summarize what a
reviewer should check most carefully. This risk is accepted and documented rather
than claimed to be solved.

## 13.9 Transport and headers

- TLS enforced, HSTS with preload.
- Content Security Policy with no inline script execution.
- `X-Frame-Options: DENY`; the portal is never framed.
- CSRF token on every mutating route.
- Rate limits per session and per integration key on write-producing routes.
- No portfolio data in any response to an unauthenticated request, including
  error bodies.

## 13.10 Data classification

| Class | Content | Handling |
|---|---|---|
| Internal | Titles, stages, lanes, plants | Visible to all authenticated employees |
| Restricted | Business cases, cost, value figures, named roles | `view_all` holders and named participants |
| Confidential | Use cases marked confidential at intake | Restricted repository access; recorded reason required |
| Personal data | Names, mail addresses of participants | See [14](14-compliance.md) |

Personal data in the portal is limited to work-role identification: who requested,
who sponsors, who approved. No performance data, no behavioural data, no
productivity measurement.

## 13.11 Logging

| Logged | Not logged |
|---|---|
| Authentication events | Session tokens |
| Authorization decisions with capability and outcome | Secrets, credentials, keys |
| API route, actor, outcome | Full intake text in application logs |
| Agent traces ([08.8](08-ai-architecture.md#88-trace-model)) | Model prompt contents beyond the trace record |
| Webhook verification outcomes | Raw webhook bodies on failure |

Intake text lives in the repository, which is the system of record. Duplicating
it into application logs would create an uncontrolled second copy with different
retention.

## 13.12 Threat model

| Threat | Control | Residual |
|---|---|---|
| Stolen session | Short lifetime, SameSite, capability re-check per request | Actions within that user's authority possible |
| Portal compromise | Cannot merge; CI enforces independently | Gate PRs could be opened at volume — detectable |
| Malicious insider with gatekeeper role | Separation of duties, self-approval rule, full audit trail | Collusion between two approvers not prevented |
| Prompt injection via intake | Wrapping, structural tool absence, human merge | Misleading draft merged without review |
| Credential leak | Encrypted env only, rotation, never in previews | Window between leak and rotation |
| Webhook forgery | HMAC before parse, replay window | — |
| Supply chain | Pinned dependencies, review on update, no runtime code from repositories | — |
| Data exfiltration via agent | Agent reads only within session visibility; traces record every read | User could read what they are already permitted to read, faster |

The last row is honest: the agent makes permitted access more efficient. That is
its purpose. The control is that visibility scoping is enforced identically for
agent and human, and that every agent read is traced.

## 13.13 Incident response

| Event | Immediate action |
|---|---|
| Suspected credential compromise | Rotate; revoke installation tokens; review recent pull requests by the application identity |
| Suspected prompt injection | Kill switch ([08.9](08-ai-architecture.md#89-operational-controls)); review traces for the window; audit `agent-proposed` pull requests merged since |
| Unauthorized gate passage | Review merge event in the repository platform audit log — outside portal control, therefore trustworthy |
| Portal compromise | Disable installation; portal loses all write capability; repositories unaffected |

Disabling the application installation is the single containment action that
removes all portal write capability while leaving the use-case fleet fully
functional. This is the containment property the architecture is designed to
provide.

## 13.14 Review before production

- [ ] Identity provider registration approved; redirect URI on the final hostname
- [ ] Application identity permissions reviewed and minimized
- [ ] Data residency confirmed, region pinned
- [ ] Model service processing terms reviewed; no training on submitted content
- [ ] Injection evaluation set passing
- [ ] Kill switch tested in production configuration
- [ ] Secret rotation runbook written and rehearsed
- [ ] Penetration test of the webhook and intake routes
- [ ] Works council engagement complete ([14](14-compliance.md))
- [ ] Retention periods configured and verified
